## 2. 模擬系統實作規劃

### 驗證

第一階段的驗證以單元測試為主，目標是先確認 `ExperimentSpec`、`ProblemRepository`、`SolverRegistry`、`Simulator`、`Validator`、`ResultWriter` 之間的契約正確。  
以下測試清單優先採用 fixture、mock、stub、in-memory writer 等方式，避免一開始就把測試耦合到大量外部檔案與完整批次流程。

#### 1. Command / App / ExperimentSpec

`UT-EXP-001`
- 測試描述：合法的命令列參數可以正確建立 `ExperimentSpec`。
- 測試方法：準備一組合法 CLI 輸入，包含 problem 清單（對應 `configs/problems/` 下存在的 yaml 路徑）、solver 清單（對應 `configs/solvers/` 下存在的 yaml 路徑）、repeat 次數、base_seed、output 路徑，呼叫 `Command / App` 的 parse 與 validate 流程。
- 預期結果：成功產生 `ExperimentSpec`，且 `problem_ids`、`solver_ids`、`repeat`、`base_seed`、`output_dir` 欄位內容與輸入一致，無錯誤回傳。

`UT-EXP-002`
- 測試描述：指定 problem 對應的 yaml 檔案不存在時，系統會在模擬開始前 fail-fast。
- 測試方法：建立一組輸入，其中 problem 清單包含 `configs/problems/` 下不存在的 yaml 路徑，執行前置驗證流程。
- 預期結果：回傳明確錯誤，指出缺少哪個 problem 的 yaml；`Engine` 與 `Simulator` 不應開始執行。

`UT-EXP-003`
- 測試描述：指定 solver 對應的參數 yaml 檔案不存在時，系統會在模擬開始前 fail-fast。
- 測試方法：建立一組輸入，其中 solver 清單包含在 `configs/solvers/` 下不存在的 yaml 對應 id，執行前置驗證流程。
- 預期結果：回傳明確錯誤，指出缺少哪個 solver 的 yaml；`Engine` 與 `Simulator` 不應開始執行。

`UT-EXP-004`
- 測試描述：缺少必要 CLI 參數（例如未指定 solver 或未指定 output）時，系統會在驗證階段拒絕建立 `ExperimentSpec`。
- 測試方法：建立缺少必要欄位的 CLI 輸入，執行 validate 流程。
- 預期結果：回傳明確錯誤，指出缺少哪個必要參數，且不產生可執行的 `ExperimentSpec`。

`UT-CNV-002`

- 測試方法：以 `mk_gk01.txt` 的內容為輸入，呼叫 `parse_gk` parser，檢查輸出的 yaml 結構。
- 預期結果：除 `best_known: null` 外，其餘欄位內容正確，維度一致性驗證通過。

`UT-CNV-003`

#### 3. ProblemRepository / ProblemModel

`UT-PRB-001`
- 測試描述：合法的標準 yaml 可以正確載入為 `ProblemModel`。

- 預期結果：成功回傳 `ProblemModel`，且 `items`、`dim`、`values`、`weights`、`capacities`、`problem_id` 欄位內容正確。

`UT-PRB-002`

- 測試方法：分別準備缺少 `values`、缺少 `weights`、缺少 `capacities` 的 fixture yaml，各自呼叫載入流程。
- 預期結果：回傳明確錯誤，指出缺少的欄位名稱（`values` / `weights` / `capacities`），且不建立 `ProblemModel`。

`UT-PRB-003`

- 預期結果：回傳維度不一致錯誤，指出哪個欄位長度與宣告的 `items` 或 `dim` 不符，且不建立 `ProblemModel`。

`UT-PRB-004`
- 測試描述：`best_known` 為 `null` 時，`ProblemRepository` 會拒絕載入並回報錯誤。
- 測試方法：準備一份所有欄位合法但 `best_known: null` 的 fixture yaml，呼叫載入流程。

`UT-PRB-005`
- 測試描述：重複載入同一個 problem 時，Repository 可以使用快取避免重複解析。
- 測試方法：使用帶有 spy/parser 計數器的 `ProblemRepository`，對同一個 problem id 連續呼叫兩次 `load`。
- 預期結果：第二次讀取直接命中快取，解析器不應重複執行，且兩次結果內容一致。

- 測試方法：註冊一個 stub solver，呼叫 `SolverRegistry.get(solver_id)` 或對應建立流程。

`UT-SLV-002`
- 測試描述：未註冊的 solver 會被 `SolverRegistry` 拒絕。
- 測試方法：直接查詢不存在的 solver id。
- 預期結果：回傳明確錯誤，不應建立任何 solver instance。

`UT-SLV-003`
- 測試描述：solver 執行後回傳的 `RunResult` 具有必要欄位。
- 測試方法：使用一個 stub solver，輸入固定 `ProblemModel`、solver config（含合法的 `stop_condition` 與 `params`）、以及 `numpy.random.Generator` 實例，呼叫 `solve`。
- 預期結果：回傳的 `RunResult` 至少包含 `best_solution`、`best_objective`、`feasible`、`evaluation_count`、`stop_reason`、`runtime`、`error` 欄位。

`UT-SLV-004`
- 測試描述：Gurobi adapter 能將求解結果轉成統一的 `RunResult` 格式。
- 測試方法：以 mock Gurobi adapter 或 stub exact solver 回傳固定解與目標值，檢查 adapter 的輸出格式。
- 預期結果：輸出欄位與一般 solver 一致，呼叫端不需要為 Gurobi 撰寫特殊分支。

`UT-SLV-005`
- 測試描述：solver config 中 `stop_condition.type` 為 `max_iterations` 時，solver 應在達到迭代上限後停止並回傳對應的 `stop_reason`。
- 測試方法：準備 `stop_condition: {type: max_iterations, max_iterations: 10}` 的 solver config，以 stub solver 執行。
- 預期結果：solver 在第 10 次迭代後停止，`stop_reason` 為 `max_iterations_reached`。

#### 5. Simulator / ExperimentRunner（含 RNG 行為）

`UT-RNG-001`
- 測試描述：相同的 base_seed 與相同的 task 展開順序，應為相同 task 產生相同亂數序列。
- 測試方法：以相同 `base_seed` 展開相同 `ExperimentSpec`，對同一個 task index 取得兩個 RNG 實例（`numpy.random.Generator`），各自取前 N 個亂數值。
- 預期結果：兩組亂數序列完全一致，確認 `numpy.SeedSequence.spawn` 的可重現性。

`UT-RNG-002`
- 測試描述：不同 task index 應產生不同 RNG 序列。
- 測試方法：固定 `base_seed`，取出 task index 0 與 task index 1 的 RNG，各自取前 N 個亂數值。
- 預期結果：兩組亂數序列不同，確認不同 task 的 `Generator` 彼此獨立。

`UT-RNG-003`
- 測試描述：不同 run 的 RNG 狀態彼此獨立，一方多取亂數不影響另一方。
- 測試方法：建立兩個不同 task index 的 `Generator`，其中一個先多取若干次亂數，再比較另一個 `Generator` 的輸出序列是否仍符合預期。
- 預期結果：每個 `Generator` 只受自身消耗影響，不受其他 run 狀態干擾。

`UT-SIM-001`
- 測試描述：`Simulator` 能依照 `ExperimentSpec` 正確展開 `RunTask`，且展開時同步預計算 `seed`。
- 測試方法：建立包含 2 個 problem、2 個 solver、3 次 repeat 的 `ExperimentSpec`，呼叫 task 展開流程。
- 預期結果：成功建立 12 個 `RunTask`，且每個 task 具備正確的 `problem_id`、`dataset`、`solver_id`、`repeat_index`、`seed`（`seed` 由 `SeedSequence(base_seed).spawn(12)[task_index]` 衍生）。

`UT-SIM-002`
- 測試描述：單次 run 執行時，`Simulator` 會將正確的輸入傳給 solver，且使用 `RunTask.seed` 建立 RNG。
- 測試方法：以 mock `ProblemRepository`、mock solver、mock `ResultWriter` 建立單次 run，執行 `Simulator.run_task(...)`；`RunTask` 應已包含預計算的 `seed`，Simulator 內部應以 `numpy.random.default_rng(seed)` 建立 `Generator`。
- 預期結果：solver 收到的 `ProblemModel`、solver config、`numpy.random.Generator`（由 `seed` 衍生）與 `RunTask` 定義一致，並在成功後寫出結果。

`UT-SIM-003`
- 測試描述：當 `ProblemRepository` 載入失敗時，`Simulator` 會立即中止整批模擬（同批次所有剩餘 task 均不執行）。
- 測試方法：準備包含 3 個 task 的批次；讓 mock `ProblemRepository` 對第 1 個 task 回傳 yaml 缺失錯誤，執行批次流程。
- 預期結果：錯誤被向上拋出或標記為 batch failure；第 2、3 個 task 的 solver 不應被呼叫；已執行 task 的結果不需要回滾。

`UT-SIM-004`
- 測試描述：當 solver 參數 yaml 缺失時，`Simulator` 會在建立 solver 前立即中止整批模擬（同批次所有剩餘 task 均不執行）。
- 測試方法：準備包含 3 個 task 的批次；讓 solver config loader 對第 1 個 task 回傳 `configs/solvers/` 缺檔錯誤，執行批次流程。
- 預期結果：錯誤被向上拋出或標記為 batch failure；solver 不應被建立；第 2、3 個 task 均不執行。

#### 6. Validator / ResultWriter / Summary

`UT-VAL-001`
- 測試描述：`Validator` 能正確判斷可行解。
- 測試方法：準備一個合法 `ProblemModel` 與一組已知可行解，呼叫可行性驗證。
- 預期結果：驗證通過，回傳 feasible 或等價的成功結果。

`UT-VAL-002`
- 測試描述：`Validator` 能偵測不可行解。
- 測試方法：準備一組刻意超過容量限制的解，呼叫可行性驗證。
- 預期結果：驗證失敗，並指出至少一個違反的 constraint 維度索引。

`UT-VAL-003`
- 測試描述：`Validator` 能偵測 solver 回傳的 objective 與重新計算結果不一致。
- 測試方法：建立一個 `RunResult`，其中 `best_solution` 正確但 `best_objective` 人為填入錯誤值，再執行 objective 驗證。
- 預期結果：驗證失敗，回報 objective mismatch。

`UT-VAL-004`
- 測試描述：`Validator` 能針對單次 run 判斷是否達到 `best_known`。
- 測試方法：準備一個有 `best_known` 值的 problem 與一個低於 `best_known` 的 `RunResult`，執行 per-run 驗證。
- 預期結果：系統能正確標示未達 `best_known`，並計算差距值，但不中止模擬（僅標記結果）。

`UT-RES-001`
- 測試描述：`ResultWriter` 能以標準格式保存單次 run 結果。
- 測試方法：建立一個完整 `RunResult`，用 in-memory writer 或暫存檔案執行寫出流程。
- 預期結果：輸出內容至少包含 `problem_id`、`solver_id`、`seed`、`best_objective`、`feasible`、`stop_reason`、`runtime`、`error` 等必要欄位。

`UT-RES-002`
- 測試描述：summary 聚合邏輯能正確依照「`feasible == True` 且 objective 驗證通過」規則計算平均值與最佳值。
- 測試方法：準備多筆固定 `RunResult`，包含三類樣本：`feasible == True` 且 objective 正確、`feasible == False`、`feasible == True` 但 objective mismatch（手算預期值），呼叫 summary aggregation。
- 預期結果：
  - 平均目標值與最佳目標值只計算「`feasible == True` 且 objective 驗證通過」的 run，與手算結果一致
  - 可行率 = `feasible == True` 的筆數 / 總執行筆數
  - 不可行 run 與 objective mismatch run 的排除筆數在 summary 中單獨列出（含原因分類）
  - 平均執行時間與平均 evaluation_count 涵蓋所有執行筆數（不論可行性）

`UT-RES-003`
- 測試描述：當某個 run 被 `Validator` 判定為異常時，結果輸出層仍能保留失敗資訊。
- 測試方法：建立一筆 objective mismatch 或 infeasible 的 `RunResult`，搭配異常狀態寫出結果。
- 預期結果：輸出中保留 `problem_id`、`solver_id`、`seed`、`error` 欄位與失敗狀態，方便後續重跑與除錯。

### 模組實作

這一段的目的，不是重複前面的模組介紹，而是將模組如何實作、彼此如何銜接、以及第一版要先做到什麼程度明確寫出來。

#### 1. 實作原則

1. 第一階段先完成「單次 run 可以正確執行」的主流程，再擴充批次執行與平行化。
2. 模組之間以明確資料契約溝通，避免 `Simulator` 直接依賴 yaml 細節，或讓 solver 直接處理輸出寫檔。
3. 模擬執行流程只讀標準 yaml，不在執行期間轉檔；缺檔或格式錯誤時直接 fail-fast。
4. 第一版先採最小可行設計，優先追求正確性、可重現性、可測試性，再處理效能與狀態重用。
5. 兩種 yaml 應分開管理：problem yaml 放在 `configs/problems/`，solver yaml 放在 `configs/solvers/`。

#### 2. 核心資料契約

在進入模組實作之前，應先定義系統內部共用的核心資料結構，因為後續模組都會依賴它們。

`ExperimentSpec`
- 角色：描述一次整批實驗的輸入規格，由 CLI 參數建立。
- 建議欄位：`experiment_id`（由 CLI 指定，用於命名輸出目錄）、`dataset`、`problem_ids`、`solver_ids`、`repeat`、`base_seed`、`output_dir`、`benchmark_enabled`。
- 用途：由 `Command / App` 產生，交給 `Engine` 與 `Simulator` 使用。

`ProblemModel`
- 角色：系統內部統一的 MKP 問題表示。
- 建議欄位：`problem_id`、`dataset`、`items`、`dim`、`values`、`weights`、`capacities`、`best_known`。
- 用途：由 `ProblemRepository` 建立，交給 solver 與 `Validator` 使用。

`RunTask`
- 角色：單次 solver 執行單位，展開時即攜帶所有執行所需的識別資訊。
- 建議欄位：`problem_id`、`dataset`、`solver_id`、`repeat_index`、`seed`。
  - `dataset`：由 `ExperimentSpec.dataset` 繼承，供 `ProblemRepository` 組合 yaml 路徑（`configs/problems/<dataset>/<problem_id>.yaml`）使用。
  - `seed`：由 `Simulator` 在展開任務時，透過 `numpy.SeedSequence(base_seed).spawn(n_tasks)[task_index]` 預先計算並寫入，使每個 `RunTask` 自身攜帶可重現的種子，執行期直接使用 `seed` 建立 `Generator`，無需重新推算。
- 用途：由 `Simulator` 根據 `ExperimentSpec` 展開，每個 task 對應一次獨立的 solver 執行。

`RunResult`
- 角色：單次執行的標準輸出。
- 建議欄位：`problem_id`、`solver_id`、`repeat_index`、`seed`、`best_solution`、`best_objective`、`feasible`、`evaluation_count`、`stop_reason`、`runtime`、`error`。
  - `seed`：固定記錄為 `RunTask.seed`（`RunResult.seed = RunTask.seed`），確保單筆輸出可獨立重跑與追蹤。
  - `evaluation_count`：計算單位為**每次個體更新**（每次呼叫 repair/improve 或更新族群中某個個體的適應值計算，視為一次 evaluation），**不等同 objective 函式呼叫次數**。不同 solver 應使用相同計算單位，以確保 summary 中跨 solver 比較的可比性。
- 用途：由 solver 回傳，交由 `Validator`、`ResultWriter`、summary aggregation 使用。

#### 3. 模組實作規劃

`1. Command / App`
- 實作目標：解析命令列，建立 `ExperimentSpec`，並在進入 `Engine` 前完成基本輸入驗證。
- 核心責任：
  - 解析 CLI 參數（problem 清單、solver 清單、repeat、base_seed、output、experiment_id 等）
  - 驗證 problem / solver / output / repeat 等輸入是否合法
  - 檢查指定 problem 的標準 yaml 是否存在於 `configs/problems/`
  - 檢查指定 solver 的參數 yaml 是否存在於 `configs/solvers/`
- 第一版完成標準：能從一組合法 CLI 輸入建立 `ExperimentSpec`；若 problem yaml 或 solver yaml 缺失，會在此階段直接終止。

`2. ProblemModel`
- 實作目標：定義系統內部統一的 MKP 問題資料結構，作為 solver、Validator 與 ProblemRepository 之間共用的資料契約。
- 核心責任：
  - 定義 `ProblemModel` dataclass 或 namedtuple，包含 `problem_id`、`dataset`、`items`、`dim`、`values`、`weights`、`capacities`、`best_known` 欄位
  - 欄位型別明確（例如 `values: np.ndarray`、`weights: np.ndarray`、`capacities: np.ndarray`、`best_known: int`）
  - `ProblemModel` 為唯讀物件，建立後不應被修改
- 第一版完成標準：`ProblemModel` 可被正確建立並傳遞；欄位型別與 Problem YAML Schema 定義一致。

`3. Converter`
- 實作目標：將各題庫的原始 txt / dat 檔案轉換為統一的 Problem YAML 格式，作為模擬執行前的前置資料準備工具。
- 核心責任：
  - 為每個題庫維護獨立的 parser 函數（例如 `parse_weish`、`parse_gk`），由人工確認後加入
  - 將解析後的資料依 Problem YAML Schema 輸出至 `configs/problems/<dataset>/<problem_id>.yaml`
  - 不在模擬執行主流程中被呼叫；僅由獨立的 CLI 命令觸發
- 第一版完成標準：至少實作一個題庫（例如 WEISH）的 parser；轉換後的 yaml 可被 `ProblemRepository` 正確載入。

`4. ProblemRepository`
- 實作目標：從標準 yaml 載入 `ProblemModel`，並提供唯讀快取。
- 核心責任：
  - 讀取 `configs/problems/<dataset>/<problem_id>.yaml`（dataset 與 problem_id 均由 `RunTask` 提供）
  - 驗證必要欄位、維度一致性，以及 `best_known` 非 null
  - 轉成 `ProblemModel`
  - 快取已載入的 problem（使用 dict，key 為 `(dataset, problem_id)`）
- 第一版完成標準：能正確載入合法 yaml；缺欄位、維度錯誤、`best_known` 為 null、檔案不存在時回傳明確錯誤。

`5. Solver 介面與 SolverRegistry`
- 實作目標：建立所有 solver 共用的介面與註冊機制。
- 核心責任：
  - 定義 `solve(problem, config, rng) -> RunResult`（stop_condition 已包含在 config 中，由 solver 自身讀取並控制終止邏輯）
  - 提供 solver 註冊與查詢
  - 隔離不同演算法實作細節
- 第一版完成標準：至少能註冊一個 heuristic solver 與一個 stub solver，並由 `Simulator` 統一呼叫。

`6. Simulator / ExperimentRunner`
- 實作目標：負責把 `ExperimentSpec` 轉為 `RunTask`，並執行主流程。
- 核心責任：
  - 展開 problem × solver × repeat 任務，同時以 `numpy.SeedSequence(base_seed).spawn(n_tasks)` 為每個 task 計算 `seed` 並寫入 `RunTask`
  - 逐筆向 `ProblemRepository` 取得 `ProblemModel`（懶載入＋快取），傳入 `RunTask.problem_id` 與 `RunTask.dataset`
  - 依據 `RunTask.solver_id` 載入 `configs/solvers/<solver_id>.yaml`
  - 第一版採 fail-fast：任一 task 發生 error（包含 problem yaml / solver yaml 載入錯誤與 solver 執行錯誤）即中止整批，剩餘 task 不執行
  - 使用 `numpy.random.default_rng(RunTask.seed)` 建立本次 run 的獨立 `Generator`
  - 呼叫 solver
  - 收集 `RunResult`
- 第一版完成標準：先支援同步執行即可，能穩定完成單批實驗並回傳所有結果。

`7. Validator`
- 實作目標：集中處理結果正確性檢查。
- 核心責任：
  - feasibility 驗證（per-run）：檢查 `for each dim d: sum(weights[i][d] * solution[i] for all i) <= capacities[d]`
  - objective 重算驗證（per-run）：重算 `sum(values[i] * solution[i])` 並與 `RunResult.best_objective` 比對
  - 是否達到 `best_known` 的標記（per-run，不中止模擬，僅標記差距）
  - seed 重現驗證的輔助函式
- 第一版完成標準：至少能驗證單次 `RunResult` 的可行性與 objective 是否一致，且失敗時不丟棄結果。

`8. ResultWriter / ResultStore`
- 實作目標：將單次 run 與批次 summary 以固定格式輸出。
- 核心責任：
  - 保存單次 `RunResult`（無論 `feasible` 值為何，均寫出含 `feasible`、`error` 欄位的完整記錄）
  - 聚合多次結果為 summary，排除規則如下：
    - 僅納入同時滿足 `feasible == True` 且 objective 驗證通過的 run 計算平均目標值與最佳目標值
    - `feasible == False` 或 objective mismatch 的 run：不納入平均/最佳值，並單獨統計排除筆數與原因
  - 統一輸出欄位與檔名規則
- 第一版完成標準：能輸出單次結果與 summary，不需要依賴個別 solver 自己寫檔。

---
> 以下第 9、10 項為 **Solver 模組的具體子項目實作**，對應流程規劃中的 Module 4（求解器模組），不計入核心模組數量。

`9. Gurobi Solver Adapter`（Solver 模組子項目）
- 實作目標：將 Gurobi 包成符合 solver 介面的實作，作為 Module 4 的一個具體 solver 實作。
- 核心責任：
  - 接收 `ProblemModel`
  - 呼叫 Gurobi 求解，並讀取 `stop_condition` 控制時間限制
  - 回傳標準 `RunResult`
- 第一版完成標準：在 `solver_id=gurobi` 時可走相同主流程，不需要獨立腳本。

`10. 演算法參數設定`（Solver 模組子項目）
- 實作目標：定義 solver yaml 的撰寫規範與載入流程，對應 Module 4 中 solver config 的讀取責任。
- 核心責任：
  - 將每個 solver 的參數保存為 `configs/solvers/<solver_id>.yaml`
  - 在 solver yaml 內包含 `stop_condition`（由 solver 自身讀取並控制終止）與 `params`（演算法自訂參數）兩個區塊
  - 演算法未在 yaml 中定義的參數使用演算法內部固定預設值（fixed layer）
  - 在建立 solver 前完成參數解析與驗證
- 第一版完成標準：至少能從 `configs/solvers/<solver_id>.yaml` 讀取一個 solver 的 `stop_condition` 與 `params` 區塊，並傳入 solver。

#### 4. 模組依賴順序

建議依照下列順序實作，這樣每一步都能被前面的單元測試保護：

1. `ProblemModel`、`ExperimentSpec`、`RunTask`、`RunResult`（核心資料結構定義）
2. `ProblemRepository`
3. `Converter`（獨立工具，可與 ProblemRepository 平行開發，最終須確認輸出 yaml 可被 Repository 正確載入）
4. `Solver` 介面與 `SolverRegistry`
5. `Validator`
6. `ResultWriter / ResultStore`
7. `Simulator / ExperimentRunner`
8. `Command / App`
9. `Gurobi Solver Adapter`（Solver 子項目）
10. 演算法參數設定（Solver 子項目）

這個順序的原因是：先把資料結構與底層元件做穩，再組出單次 run 主流程，最後才接 CLI、Gurobi 與參數外部化。Converter 獨立於主流程之外，可以提前完成以便準備 yaml 資料，但不阻塞主流程測試（測試可以使用 fixture yaml）。

#### 5. 第一階段里程碑

`M1. 核心資料契約完成`
- 完成 `ProblemModel`（含型別定義）、`ExperimentSpec`、`RunTask`（含 `dataset` 與 `seed` 欄位）、`RunResult` 定義。
- 對應單元測試至少通過 `UT-EXP-001`、`UT-PRB-001`、`UT-SLV-003` 的必要資料欄位檢查。

`M2. 單次 Run 主流程完成`
- `ProblemRepository`、`SolverRegistry`、`Validator`、`ResultWriter`、`Simulator` 可串成單次 run。
- 能以一個 stub solver 完整執行：載入 problem → 展開 RunTask（含預計算 seed）→ 使用 RunTask.seed 建立 Generator → 求解 → 驗證 → 寫出結果。

`M3. 批次執行完成`
- `Simulator` 可根據 `ExperimentSpec` 展開多個 `RunTask` 並依序執行。
- 可輸出批次 summary。

`M4. 真實 Solver 接入完成`
- 至少接入一個現有 heuristic solver，並確認 solver 內部亂數呼叫已改為使用傳入的 `numpy.random.Generator`，不再依賴全域 `random` 模組，以保證可重現性。
- 若需要精確方法比較，再接上 `Gurobi Solver Adapter`。

#### 6. 第一版不急著做的內容

以下內容屬於第二階段或之後再做，不應阻塞第一版主流程落地：

1. 平行執行 worker pool
2. 大型快取與 mutable state 重用
3. 跨不同優化問題的泛化抽象
4. 更完整的 benchmark pipeline

---

**Q3：新演算法的 params 驗證機制（未來完善）**

現有 Solver YAML Schema 使用開放式 `params` map，任意 key 均被接受，無法在啟動階段提前發現參數拼寫錯誤或缺漏必要參數。

待處理事項：
- 為每個 solver_class 定義 `required_params` 與 `optional_params` 規格（可放在 solver yaml 或 solver class 本身）
- `Command / App` 或 `SolverRegistry` 在載入 solver yaml 時，對照規格驗證 params 完整性，若缺少必要參數則在啟動時 fail-fast
- 目前第一版先以「執行期若取不到 param 就 KeyError / 用預設值」方式處理，不阻塞主流程

---

**Q3-2：`stop_condition.type` 擴充相容（未來完善）**

第一版先支援 `max_iterations`、`max_seconds`。後續需補上複合終止條件，避免各 solver 各自實作造成語意不一致。

待處理事項：
- 在 schema 中明確加入 `either` / `both` 的列舉與語意定義
- 明確定義 `either`（任一條件達成即停止）與 `both`（全部條件達成才停止）
- 為 `either` / `both` 補齊對應單元測試，確保不同 solver 行為一致



**Q4：跨問題型態的架構泛化（長期目標）**

第一版的 `ProblemModel`、Problem YAML Schema、`Converter`、`Validator` 均為 MKP-specific，硬編碼 MKP 的欄位（`values`、`weights`、`capacities`）與公式。若未來要支援 TSP、VRP 等問題型態：

- `ProblemModel` 需重構為抽象基底類別或 TypeVar，各問題型態繼承並定義自己的欄位
- Problem YAML Schema 需分離為 problem-type-specific schema（schema 版本或 `problem_type` 欄位識別）
- `Converter` 需對應新問題型態增加 parser
- `Validator` 需對應新問題型態提供不同的 feasibility 與 objective 計算邏輯
- Solver 介面的 `solve(problem: ProblemModel, ...)` 需配合型別安全設計（泛型或 Union）
- 建議在動工前先確立「問題型態 plugin 架構」，以免每次新增問題型態都需要修改框架核心
